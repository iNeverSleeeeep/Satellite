# AI 协作要求

本文档整理当前项目中，用户对 AI 辅助修改代码时提出的长期要求。后续如无特殊说明，默认按本文档执行。

## 分支与提交

- 默认在 `master` 分支工作，不要在非主分支上开发。
- 不要擅自创建新的工作分支，除非用户明确要求。
- 如果需要提交到 GitHub，优先直接提交到 `master`。
- 提交时只提交本次任务相关文件，不要混入无关改动。
- 如果工作区中存在无关未提交改动，必须先识别并避免误提交。

## 代码修改方式

- 面向实际工程使用场景思考，不只做能运行的占位代码。
- 对仿真代码和工程代码的边界保持清楚，避免混淆“控制级等效模型”和“更接近实机的物理模型”。
- 在合适的情况下，优先保留“简化模型 + 物理模型”的双模式结构，便于联调和高保真验证并存。
- 修改应尽量保持接口稳定，避免不必要地破坏现有调用关系。

## 注释与文档

- 新增或修改的重要算法代码，应补充详细注释。
- 注释使用中文。
- 文件编码使用 `UTF-8`。
- 注释不仅说明“做了什么”，还要解释“为什么这样做”和“算法原理”。
- 对关键控制/分配/建模逻辑，要把物理意义和工程意义解释清楚。

## 仿真建模偏好

- 当前项目是仿真项目，但建模时应考虑未来向更接近星上执行链路的方向演进。
- 不要求对所有环节都做最高精度物理仿真。
- 优先提高对闭环性能、执行器能力、时延、饱和、量化、方向约束等关键因素敏感环节的保真度。
- 对飞轮、磁力矩器、推力器等执行器，优先考虑建立更接近工程实际的物理模型。
- 能区分以下两类模型时，尽量区分清楚：
  - `ideal`：控制分配和快速联调用的等效模型
  - `physics`：更接近实机执行链路的物理模型

## 沟通方式

- 尽量减少用户重复说明要求的成本。
- 当用户已经明确表达长期偏好后，应默认延续执行，不要每次重复确认。
- 如果存在明显风险、范围混淆或可能误伤用户未提交改动，再主动提醒并确认。

## 当前已明确的长期偏好摘要

- 在 `master` 上工作。
- 不在非主分支开发。
- 提交 GitHub 时只提交相关文件。
- 提交信息使用中文。
- 代码注释使用中文。
- 文件编码使用 `UTF-8`。
- 重要算法要解释清楚。
- 对关键执行器链路，优先做更接近工程实际的建模。
